Durcir sans plugin : WAF, en-tetes et CSP

Chaque plugin installe est une surface d'attaque. L'approche que l'on prefere : poser les fondations de securite directement dans la configuration du serveur, avant meme que WordPress ne charge. Ce que le serveur gere, les attaquants ne peuvent pas le contourner via une injection dans le CMS.

Le pare-feu applicatif (WAF) au niveau serveur

Sur Apache, ModSecurity est disponible sur la plupart des hebergements mutualises. Il filtre les requetes malformees et les signatures d'attaque connues (injections SQL, tentatives de traversee de repertoire, scanners automatiques) avant qu'elles n'atteignent PHP. Activez-le depuis votre panneau et selectionnez un jeu de regles OWASP de base.

Sur Nginx ou en frontal Cloudflare, vous disposez de regles WAF equivalentes. Cloudflare en offre meme un ensemble gratuit qui bloque les attaques les plus communes sur WordPress, dont les tentatives en masse sur xmlrpc.php et wp-login.php.

Bloquer xmlrpc.php quand vous ne l'utilisez pas est l'une des mesures les plus efficaces. Ajoutez dans .htaccess : <Files xmlrpc.php> Order Deny,Allow Deny from all </Files>

Les en-tetes de securite HTTP

Ces en-tetes s'ajoutent dans .htaccess (Apache) ou dans la configuration Nginx. Ils instruisent le navigateur sur ce qu'il est autorise a faire avec votre contenu.

  • X-Frame-Options: SAMEORIGIN interdit l'inclusion de votre site dans une iframe tierce, contre le clickjacking
  • X-Content-Type-Options: nosniff empeche le navigateur de reinterpreter le type MIME d'un fichier
  • Referrer-Policy: strict-origin-when-cross-origin limite les informations transmises lors des clics sortants
  • Permissions-Policy desactive les API navigateur que vous n'utilisez pas (camera, microphone, geolocation)
Header always set X-Frame-Options "SAMEORIGIN"
Header always set X-Content-Type-Options "nosniff"
Header always set Referrer-Policy "strict-origin-when-cross-origin"

La politique de securite du contenu (CSP)

La CSP est l'en-tete le plus puissant, et le plus delicat a configurer. Elle definit precisement d'ou votre page peut charger des scripts, des styles, des images. Une CSP bien rediglee rend les attaques XSS quasiment inoperantes, meme si du contenu malveillant parvient a s'injecter dans votre base de donnees.

La difficulte vient des extensions WordPress, qui chargent souvent des ressources depuis des domaines tiers (Google Fonts, CDN analytiques, boutons sociaux). La methode la plus sure : activez d'abord en mode Content-Security-Policy-Report-Only, observez les violations dans les logs navigateur pendant une semaine, puis construisez votre politique sur la base des ressources reellement utilisees.

Commencez permissif, puis resserrez. Une CSP trop stricte casse votre site en silence (images manquantes, boutons inactifs) sans avertissement visible.

Le guide complet avec les configurations .htaccess et les exemples CSP pour WordPress est disponible sur wpadminlab.com : securiser WordPress, WAF, headers et CSP. Pour diagnostiquer l'etat de securite de votre installation avant de configurer quoi que ce soit, le scan WordPress gratuit est un bon point de depart.
